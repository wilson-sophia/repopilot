# 执行检查点与中断恢复

## 恢复语义

运行记录增加版本化JSON检查点，保存已完成模型步骤的消息、累计步数、已提交正文和源码提交快照。启动恢复进程只处理 `running` 任务，保留原任务ID、工具记录、来源编号和用量，不再清空从头调研。

- 完成模型步骤后保存assistant/tool消息，下次模型请求从该对话位置继续，总执行步数沿用原预算。
- 已完成的只读工具按名称和参数复用持久结果；正在执行但未完成的工具可以重试，并复用原记录ID。当前工具都是查询类，不承诺外部写操作的exactly-once语义。
- 源码目录快照随检查点保存，恢复后仍按相同提交读取，不因默认分支变化混合版本。
- 模型流式生成中断时，回到最近已提交的模型步骤，重新生成该未完成步骤。不能从供应商中断的Token或内部推理状态精确继续；UI中未提交的正文可能回退至检查点正文。
- 终稿已生成、状态尚未写成完成时，可从finalizing检查点完成来源追加和终态保存。
- 写入按调用顺序排队，终态仍依赖数据库的 `status = running` 条件保护；用户主动取消的任务不被恢复。
- 连接中断不会当作用户主动取消；保存为running，等待启动恢复进程。当前恢复由服务重启触发，没有额外的在线调度队列。
- 演示模式复用已完成工具并从已保存报告前缀继续。旧任务没有模型检查点时无法还原未保存的对话，只能利用已有工具结果重新建立模型上下文。

新增列随启动初始化幂等迁移，不删除原项目和资料。检查点是服务端执行状态，不表示公开GitHub仓库已同步本地修改。

## 验证

自动化进程强杀用例 `tests/research-unit/checkpoint-restart.test.ts`：真实启动恢复子进程，完成一次源码工具调用，在下一次模型请求挂起时强杀进程，再启动新进程；断言模型收到已保存工具消息、工具和来源ID不变、模型累计步数继续增加，报告最终完成。

真实浏览器实验在隔离数据库与本地端口完成：真实模型第1步完成后强杀整个服务进程树，再启动服务；同一任务从第1步继续到第4步完成，原有1条完成工具记录与4个来源保留，后续新增2条工具记录及1个来源。浏览器刷新后能查看最终报告。

单元和契约回归45项、API与浏览器回归26项通过。用户数据与真实密钥没有写入验证产物。

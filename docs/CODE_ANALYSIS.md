# 源码驱动的仓库调研

技术实现的主要依据改为源码，需求文档用于判断是否符合业务需求，仓库介绍和Issue仅作为背景与待核实线索。

## 读取流程

`analyzeRepository` 解析绑定仓库默认分支，固定到提交SHA，获取递归目录并按问题和入口文件启发式选择最多4个文件。模型根据返回目录再调用 `readRepositoryFile(path, startLine)` 补充证据。一次调研复用同一提交快照，文件按该快照记录的blob SHA读取，不随分支更新漂移。

源码来源保留文件路径、起止行、提交SHA、带行号原文和GitHub固定提交链接，沿用现有来源预览、报告导出和历史持久化。无需修改文档RAG的上传与索引机制。

工具循环仍最多6步，但最后一步关闭工具调用，专用于形成报告，避免持续补读耗尽步数却不输出正文。此边界由模型请求配置控制，而非只依赖提示词。

## 边界

- 只读取公开GitHub仓库，不克隆、不执行源码、构建脚本或测试，不访问文件中提供的任意URL。
- 目录最多保留10000个可读文件，提供给模型的目录最多300个路径；GitHub截断或本地限额触发时返回标识。目录选择是启发式，不是全仓库代码语义搜索。
- 跳过依赖、构建产物、锁文件、环境文件、二进制及符号链接。文件最大200KB，每次最多150行、12000字符；可继续按行补读。
- GitHub JSON响应最多5MB；固定API来源、禁止重定向，保留超时、取消和有限重试。
- 所有源码视为不可信资料，不能覆盖系统指令与工具权限。
- 真实模式绑定仓库的调研必须取得源码证据，否则终态为失败，避免只凭元数据给出实现结论。读到源码不表示已经验证行为，报告需区分观察、推断与待运行验证事项。
- 演示模式展示确定性的源码证据整理，不声称调用模型分析。自动化fixture源码与真实GitHub服务分开验证。

# 从“运行项目”到“讲清项目”

## 建议学习路线

先按 README 启动，用示例文件完成一次调研，再打开开发记录和架构说明。第一次阅读只跟一条请求：创建项目 → 导入资料 → 提问 → 工具事件 → 报告 → 引用 → 历史。之后再读错误与授权分支。

可以在每个节点暂停，自己预测下一次网络请求、数据库变化和界面变化。若预测与运行结果不同，回到对应函数定位原因，比逐文件通读更容易建立整体理解。

## 五分钟演示

1. 新建一个公开开源仓库的调研项目，解释目标用户和决策问题。
2. 导入 `examples/editor-requirements.md`，展示处理状态。
3. 询问“结合我们的 React 和中文需求，这个项目有哪些需要核实的接入风险？”
4. 展示工具执行卡片，说明接口返回的事实、资料来源和时间。
5. 打开引用原文，核对一个结论是否有依据。
6. 导出报告，再展示资料不足或工具失败时的反馈。
7. 明确当前使用的是演示执行还是真实模型，说明相应验证范围。

## 可以讲的技术取舍

- 为什么一周内选择 Node.js + TypeScript？共享类型解决了什么，运行时校验又解决了什么？
- 为什么要把报告文本、工具状态和引用分开建模？
- 流式事件到达时，怎样避免丢失增量或重复添加工具卡片？
- 资料为什么要分块与重叠？片段过长或过短分别有什么代价？
- Embedding 和普通关键词匹配有何区别？本地哈希演示有什么限制？
- 知道文档 ID 后为什么仍不能直接读取？授权校验应该放在哪里？
- 用户取消请求时，前端停止显示与后端停止执行有什么区别？
- 工具重试为什么需要有次数和时间上限？哪些操作不能简单重试？
- 保存历史与后台任务断点恢复的边界是什么？
- 为什么自动化测试需要固定夹具，同时还要保留真实外部服务验证？

## 用证据支持贡献

面试时把能力分成三类说明：

- **继承**：Vercel Chatbot 已有的 Next.js 工程、Auth.js 身份、基础对话与 UI 组件。
- **新增**：调研项目领域、资料导入与检索、三个工具、执行过程与引用、报告管理及相应测试。
- **待验证或后续**：当前未跑通的外部模型联调、没有测量的规模或性能、多实例和持久任务恢复。

使用 AI 辅助开发的事实可以公开说明；关键是能解释自己验证了什么、纠正了哪些错误以及为什么接受最终设计。

## 简历写法

完成验证后可使用这样的基本描述，并按真实结果补充：

> 基于 Vercel Chatbot 实现开源项目调研 Agent 工作台，新增项目资料导入、文档检索与仓库 / Issue 查询工具；通过结构化执行事件展示工具状态和引用证据，支持报告历史与 Markdown 导出；为权限隔离、工具异常及核心用户流程建立自动化验证。

不要把模板已有功能写为从零自研。没有实际测量时，不填成功率提升、用户规模、成本降低或性能提升百分比。

## 自查练习

修改一处需求，再完整走一遍实现：

1. 把单文件大小限制调整为另一数值，找出服务端和界面如何同步。
2. 给工具加入一个可识别的失败，确认错误、持久记录和重试表现。
3. 用两个浏览器会话尝试读取同一资源，解释访问控制结果。
4. 把文档的一条需求改掉，确认重新导入后报告引用反映了新证据。
5. 阅读一条失败评测案例，决定应修检索、提示词、工具还是产品反馈。
